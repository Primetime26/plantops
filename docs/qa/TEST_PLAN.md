# План тестирования PlantOps

## Объект и цель

Один React/Express продукт, два адаптера хранения. Проверяется корректность операционного цикла, изоляция публичных посетителей, сохранность локальной истории и работоспособность в ограниченной памяти. Учебная физическая модель не валидируется для реальной эксплуатации.

## Риски и приоритеты

| Риск                                               | Приоритет | Метод                                                              |
| -------------------------------------------------- | --------- | ------------------------------------------------------------------ |
| Состояние одного посетителя видно другому          | P0        | Два Supertest agent, чужой ID, чужие действия; два browser context |
| Повторные аварии или потерянная история            | P0        | Порог/эскалация/ack/reset, повторные и конкурентные команды        |
| Потеря версии заявки                               | P1        | Одновременный PATCH с одной version, 200 + 409                     |
| Память выше бесплатного runtime                    | P1        | Полные лимиты всех сессий, конкурентные ответы, RSS                |
| Холодный старт / перезапуск оставляет сломанный UI | P1        | 503 + retry; действительный restart процесса; SESSION_RESET        |
| Данные Local теряются                              | P1        | Новое подключение Prisma после записи, реальные миграции           |
| Обход переходов / произвольный ввод                | P1        | Негативные REST-кейсы, терминальные статусы, XSS-текст, CSV        |
| Непригодный интерфейс                              | P2        | Desktop/tablet, клавиатура, пустые состояния, графики              |

## Уровни и среда

- Unit — Vitest, чистые функции, фиксированное время, без таймеров и сети.
- Integration — Supertest + настоящий Express; отдельная временная SQLite на каждый тестовый файл, миграции через Prisma CLI; demo с управляемыми часами, независимые agent-cookie.
- E2E — Playwright Chromium, собранные frontend/backend, отдельные порты 3100 и 3101. Второй процесс используется для проверки перезапуска. Не использовать рабочую БД.
- Ресурсы — Node 24, ограниченная V8 heap, полный bounded dataset; измерение RSS не эквивалентно cgroup и CPU Layero.
- Ручная приёмка — Node/macOS, поддерживаемый браузер; после публикации дополнительно HTTPS, приватное окно, действительный холодный старт.

## Данные

Пять seed-активов. Для тестов заявок используются роли «Механик», «Оператор», а не персональные данные. Unit/API время подменяется; E2E использует реальное серверное время и ожидаемые состояния, без ускоряющего тестового endpoint в production. SQLite-тесты очищают только свою временную БД. Изменения browser demo можно сбросить.

## Критерии входа / выхода

Вход: зависимости из lock-файла установлены, Prisma Client сгенерирован, свободны тестовые порты, Chromium установлен.

Выход для серверного слоя: типизация и все unit/API-тесты зелёные, production build успешен, ресурсный сценарий ниже 230 МиБ на проверенной среде, критические дефекты устранены.

Выход для релиза: дополнительно успешный E2E в среде, разрешающей запуск браузера, просмотр артефактов/верстки и smoke на фактическом Layero Free. Если браузер заблокирован средой, это статус BLOCKED, а не PASS. Наличие workflow не подтверждает remote CI.

## Не входит

Пентест, длительный soak, промышленная сертификация, реальные датчики, гарантии multi-pod, WebKit/Firefox/Windows-прогон в этой итерации. Для этих областей не делать выводов на основе Chromium или Supertest.

## Команды и отчётность

Команды находятся в README. После прогона обновлять `docs/VERIFICATION.md`: дата, версии, команды, количества, фактические результаты и ограничения. Дефекты оформлять по шаблону, привязывая регрессионный тест. При неудаче CI сохраняет trace/screenshot/report на 7 дней. Не помещать cookie или локальные базы в публичные отчёты.
